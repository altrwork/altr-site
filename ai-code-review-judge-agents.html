AI code review with judge agents: several narrow reviewers, one verifier, and a human who merges.

An AI reviewer that comments on everything gets muted within a week. One that finds a real bug and proves it gets read. The difference is almost entirely in how the review is structured, not which model runs it.

Short answer

AI code review with judge agents runs several model reviewers over a pull request, each looking for one class of problem, then passes their findings to a verifier that checks each against the actual code and drops what it cannot confirm. What survives is ranked by severity and posted with file and line evidence. The agents flag. A person still decides whether to merge.

How does a judge-agent review work?

Split the review into roles, the way a senior team would.

  1. Finders. Several agents read the diff and the code around it, each with one focus: logic errors, security, data integrity, API compatibility, migration safety.
  2. Verifier. A separate pass checks every candidate finding against the code's actual behavior and discards what it cannot confirm. This is the step that keeps false positives down.
  3. Reporter. Duplicates are merged, findings are ranked by severity, and each is posted on the line it concerns, with a summary at the top.

Anthropic's managed Code Review for Claude Code works this way. As of September 2026 it is a research preview for Team and Enterprise plans: several agents analyze the pull request in parallel, a verification step filters false positives, and findings are tagged Important, Nit or Pre-existing. It never approves or blocks a pull request. Its check run always finishes neutral, so any merge gate is one you build yourself.

What severity rubric should an AI reviewer use?

A short one, written down, that the humans already agree with. Without it, review becomes a stream of preferences.

LevelMeansExamples
ImportantFix before mergeWrong logic, data loss, a query not scoped to the tenant, secrets or personal data in logs, a migration that cannot roll back
NitWorth fixing, not blockingMisleading names, a missed edge case in a helper, a rule from the repo's instructions broken
Pre-existingA real bug this PR did not introduceReport once, route to the backlog, do not hold the PR
Do not reportAnything CI already enforcesFormatting, lint, type errors, generated files, lockfiles

Require evidence for every Important finding: the file and line, what happens, and how to reproduce or check it. A finding inferred from a function's name, rather than its code, is the usual false positive.

How do you tune what the reviewer flags?

Put review rules in the repository, next to the code. Claude's Code Review reads the repo's CLAUDE.md as general context and a REVIEW.md at the root as review-only instructions. The same content works as the system prompt for a reviewer you run in your own CI.

# Review instructions

## Important means
Incorrect logic, unscoped database queries, personal data in logs,
and migrations that are not backward compatible. Style is Nit at most.

## Limits
Report at most five Nits. Mention the rest as a count in the summary.
After the first review, post new Important findings only.

## Do not report
Lint, formatting, type errors. Anything under src/gen/ or any *.lock file.

## Always check
New API routes have an integration test.
Behavior claims cite file:line in the source, not a guess from a name.

Keep it short. Anthropic's own guidance is that a long review file dilutes the rules that matter.

How do you know the reviewer is worth keeping?

Measure it like any other reviewer, for a month, before deciding.

  • Acceptance rate: findings that led to a code change, out of findings posted.
  • False positives: findings dismissed as wrong. Thumbs-down reactions on comments are a cheap way to count them.
  • Escaped defects: bugs found after merge in code the reviewer saw. This is the number that justifies the cost.
  • Noise: comments per PR, and how many were Nits. Rising nits with flat acceptance means the rubric needs tightening.

If acceptance is low after a month of tuning, narrow the reviewer to the one class of bug it catches reliably, or turn it off.

Where does AI review go wrong?

  • Nit floods that train the team to ignore every comment, including the real one.
  • Endless re-review, where each push produces new style comments on a one-line fix.
  • Reviewing code nobody wrote: generated clients, vendored code, lockfiles.
  • Untrusted pull requests. A PR from outside can carry text aimed at the reviewer. Claude's Code Review reviews a fork's PR only when a maintainer asks it to, which is a sensible default for any setup.
  • Treating silence as approval. "No issues found" means none the reviewer could verify, not that the change is safe.
Working rule

Let judge agents find and prove problems. Keep the decision to merge with the engineer who owns the change.

Common questions

Can an AI agent approve a pull request?

It can be wired to, but it should not be the approver. Anthropic's managed Code Review deliberately never approves or blocks a PR, and its check run always completes as neutral. Use AI findings as input, gate merges on your own tests and rules, and keep a person as the approver.

How much does AI code review cost?

It depends on the size of the change and how often reviews run. As of September 2026, Anthropic's docs put its managed Code Review at an average of $15 to $25 per review, billed on usage. Running a reviewer in your own CI costs the API tokens it uses. Reviewing on every push multiplies the cost.

What is a judge agent?

A judge agent is a language model given a specific job of evaluating something, such as a code change, against a written rubric and returning a verdict with evidence. In code review, several judges usually look for different problems, and a separate verifier checks their findings before anything is posted.

Does AI code review replace human reviewers?

No. It is good at catching specific classes of bug early and at reading every line consistently. It does not know the product intent, the trade-offs the team made, or what the customer needs. Human review moves toward design and intent, and the merge decision stays with a person.

How do you reduce false positives in AI code review?

Add a verification step that checks each finding against the actual code, require a file and line for every serious finding, tell the reviewer what not to report, cap minor comments, and track which findings were dismissed so you can tighten the rubric.
