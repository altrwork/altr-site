How we run altr on our own AI operating system.

altr is three people. We run the company's chat, wiki and CRM on software we wrote ourselves, behind one login, and four AI agents work in that software the same way a teammate does. They have accounts, they post in channels, they edit pages, and they update CRM records. This page explains how it is put together, why we made each choice, and what we checked along the way.

It is written for people who build things. If you only want the idea, read the next section and the walkthrough of Kara. If you want the mechanisms, keep going.

The short version

  • Four apps on Cloudflare. altr-auth (login, directory, OAuth), altr-chat (Slack-like), altr-docs (Notion-like) and altr-crm (HubSpot-shaped). Each is one Cloudflare Worker. Data lives in D1 (SQLite), file bytes in R2, and Durable Objects hold live connections.
  • One login. People sign in once with Google through Cloudflare Access. Every app checks that identity itself and asks altr-auth whether the person is still active.
  • Every app is also an MCP server. Claude, and our agents, connect to the same apps people use and read and write the same records. There is no separate "AI database".
  • Four agents: Kara takes intake calls, Counsel drafts documents and invoices, GTM drafts follow-up emails and preps us for meetings, and Engy builds and fixes our internal software.
  • Agents are code. Each one is a manifest file in a git repo. A merge deploys it. The login server enforces what any agent may be given, no matter what the manifest says.
  • About 30,000 lines of TypeScript and SQL across the four apps, and about 285 commits across eight repositories since October 1, 2026. The four platform repositories begin between October 6 and October 9, and the last commit described here is from October 15.
  • Platform infrastructure costs about $0 to $0.20 a month on top of the $5 Workers Paid plan we already had. Model usage is separate and capped per agent.

Why we built it

We wanted five things:

  1. One login for people, with no password system of our own to defend.
  2. Agents as full members of the workspace, reachable through MCP, not bolted on through screen scraping or one-off scripts.
  3. A record that cannot be lost: soft deletes, point-in-time restore, and encrypted off-database copies.
  4. Agents that cannot do more than we allowed, with the limits enforced in code and not in a prompt.
  5. A system small enough that three people can operate it, and that we can describe in one document.

The rest of this page is what those five goals turned into.

Why this matters for a small team

A three-person company has the same jobs as a thirty-person one and a third of the hours. Someone has to take the first call with a new lead, write the follow-up, file the notes, draft the proposal, send the invoice, remember who spoke to whom last week, and fix the broken thing in the internal tools. When the same people also do the client work, those jobs either get squeezed or get done at night.

Agents change that only if they can be trusted with real work. A chatbot that answers questions in a separate window does not take a job off anyone's plate, because a person still has to copy its output into the CRM, the wiki and the email. What takes the job off is an agent that works inside the same systems the team uses, under the same login, with limits the team has chosen.

That is what we built, and it is why the agents here are not a separate product bolted on the side:

  • They act in the systems of record. Kara's call ends up as a CRM record, a docs page and a chat post. Counsel's draft invoice is a real Stripe draft with a note on the CRM deal. GTM's follow-up is a draft in the seller's own Gmail. Engy's change is a real pull request. Nobody retypes anything.
  • They act under limits. Each agent has one job, a daily spend cap, a list of what it may do alone and what needs a person, and a list of what it will never do. The three of us can hold a list that short in our heads.
  • They leave a trail. Every call an agent makes is in an audit log with the credential it used. When something looks wrong, we can see what happened and switch the agent off in one step.
  • They stay inside the team's attention. The questions, the approvals and the results all show up in chat, where we already are. Approving an invoice is replying "approve" in a thread.

We should be plain about what we have and have not measured. We have not timed how long the team used to spend on these jobs, so this page does not claim a number of hours saved. What we can state is what changed in who does the mechanical half: the intake call, the notes, the first draft of a document, the follow-up email, the CRM entry and the first pass at a small code change are now done by an agent and reviewed by a person. The judgment half, who to work with, what to promise, and whether to merge, stays with us on purpose.

Decisions that shaped it

One Worker per app, no framework

Each app is a single Worker with a hand-written router: dispatch on the URL path in src/index.ts, about fifty lines. Every app already worked that way before we wrote it down, and it keeps bundles and cold starts small. The auth Worker bundles to 27 KB gzipped, chat to 168 KB, docs to 466 KB.

D1 holds relational data. R2 holds file bytes. Durable Objects are used only where something has to stay connected: the chat rooms and the document editor.

A written standard, checked by a script

The four apps follow one standard (altr-app-standard/1). It fixes the layout of the repository, the pinned version of every dependency (exact versions, no ranges), the shape of IDs (<prefix>_<ULID>), the shape of timestamps (UTC ISO 8601), the error format, the security headers, the audit table, and the names of the MCP tools.

A script, conformance.mjs, checks all of it against each repo. It looks at the scripts in package.json, the pinned versions, whether the vendored shared packages match their source, the migration file names, the audit table, the wrangler.jsonc settings, and conventions in the code such as the health route and the error envelope. It also checks that each README has the same sections. The point is that any of us, or any agent, can open any repo and already know where things are.

The shared code is two packages: @altr/platform (HTTP helpers, security headers, IDs, the audit writer, MCP instrumentation) and @altr/auth-client (token verification). They are copied into each app by a sync script, so every repo builds on its own in CI without reaching into another repo.

Why we wrote our own authorization server

Claude connects to a remote tool server using OAuth 2.1, and our four apps all need to accept the same tokens. We looked at the options.

Cloudflare's workers-oauth-provider library is good, but it is built for one Worker that is both the authorization server and the resource server. We needed one server that four apps trust. It stores grants in KV, which is another product with its own pricing. It seals grant properties when the person consents, which conflicts with deactivating someone and having their tokens die immediately. And its refresh-token rotation leaves the old token valid until the new one is used, which is a grace window and not reuse detection.

Better Auth and OpenAuth would have left us running password, two-factor and recovery code. Keycloak, Authentik and Zitadel need a server with Postgres. For three people that is the wrong amount to operate.

So altr-auth is its own Worker with its own D1 database. The first version was about 600 lines. With agent provisioning, admin pages and audit it is about 2,100 lines of TypeScript and SQL today. It is deliberately separate from the product we sell to clients. Internal identity never shares a database or an issuer with client systems.

We did not write our own sign-in or two-factor

A managed path already gives phishing-resistant sign-in: Google Workspace behind Cloudflare Access, with Google's 2-Step Verification, including passkeys and security keys. Writing our own WebAuthn ceremonies, authenticator secrets and account recovery would add the riskiest code in the company and protect nothing extra. Our job is narrower: verify the identity we are handed, and authorize well.

Outside data comes in once, through the CRM

This is the rule that keeps the agents simple. Gmail, Stripe, Granola and Apollo are read only by the CRM's own sync, on a schedule an admin controls. Agents never hold read credentials for those services. If an agent wants to know what a client has paid, it asks the CRM (get_stripe_billing). If it wants to know whether a teammate emailed someone last week, it asks the CRM (get_recent_touches). The manifest check rejects any agent that declares read access to Stripe, Gmail or Granola.

The other half of the rule is that doing something in an outside service belongs to exactly one agent, holding the narrowest key that works. Counsel is the only agent that writes to Stripe. GTM is the only one that writes Gmail drafts. Kara is the only one that places phone calls. There is no shared "do everything" server, and no Worker calls another agent's Worker.

Dry run first, then confirm

Every CRM write tool returns a preview and changes nothing unless the caller passes confirm: true. The preview lists exactly which records and fields would change and whether the change is valid. Agents run the preview, check valid, and then confirm. Deletes are soft everywhere: records are archived, never removed.

Identity and tokens

People

A person opens any altr app. Cloudflare Access sends them through Google sign-in and sets a session cookie for that hostname. The app receives a signed JWT in the Cf-Access-Jwt-Assertion header. The Worker does not trust the header. It checks the signature against Cloudflare's published keys and checks the issuer and the audience, so a misconfigured Access policy fails closed.

Then the Worker asks altr-auth whether this email belongs to an active person, and what their role is. The answer is cached for 60 seconds. A new person with an @altrwork.com address is added to the directory on first visit.

One decision here is worth stating. If altr-auth cannot be reached, the apps still let in a person Access has already authenticated. They fail open on that lookup only. Bearer tokens do the opposite and fail closed. We chose this because a person has already proven who they are to Cloudflare, and losing the directory should not lock the whole team out of their work, while a token is a credential we can only judge by asking.

Roles live in one place. altr-auth is the source of truth for whether someone is an admin. Chat, docs and the CRM each keep a cached copy of the role and correct it whenever altr-auth answers. Deactivating a person in altr-auth revokes every token they or their agents hold, and every app refuses them on the next request, within 60 seconds.

Agents and MCP clients

An MCP client such as Claude.ai or Claude Code finds the login server like this:

1. POST chat.altrwork.com/mcp          → 401, WWW-Authenticate points at the resource metadata
2. GET  the resource metadata          → "authorization server: auth.altrwork.com"
3. GET  auth.altrwork.com/.well-known/oauth-authorization-server
4. Browser → /oauth/authorize?resource=https://chat.altrwork.com/mcp&scope=chat:read chat:write&code_challenge=…
        Access sign-in → consent screen: which scopes, and "connect as" yourself or an agent you own
5. POST /oauth/token (code + verifier + resource)
        → access token (1 hour) + refresh token (30 days, rotated on every use)

The tokens are random opaque strings, not JWTs. altr-auth stores only their SHA-256 hashes. Each app checks a bearer token by calling altr-auth's introspection endpoint over a service binding (a direct Worker-to-Worker call, with no public network hop and no extra request fee), and caches a positive answer for 30 seconds. Because every check reads live state, revoking a token or deactivating a person takes effect within 30 seconds.

Introspection runs these checks in order: the token's hash, whether it was revoked, its expiry, its audience, whether the principal is active, whether the person acting is active, whether the owner of an agent is active, whether the token's scopes fit within the agent's current spec, and that no token carrying the provisioning scope is accepted at an app.

Token Lifetime Issued by Valid at
OAuth access token 1 hour /oauth/token after consent the one app in its audience
OAuth refresh token 30 days, sliding, rotated each use /oauth/token altr-auth only
Agent service token up to 90 days the deploy pipeline only every app its scopes cover
Deployer token up to 365 days an out-of-band script the provisioning API only, never an app
App introspection secret until rotated altr-auth admin altr-auth's introspection and directory routes

Some details that matter:

  • Audience binding (RFC 8707). A token minted for the docs MCP endpoint is inactive at chat. A leaked docs token cannot be replayed against the CRM.
  • Scopes are chat:read, chat:write, docs:read, docs:write, crm:read and crm:write. Read-only tokens are never shown the write tools, and calling one returns a 403 with a standard insufficient_scope challenge. There is no "admin" scope. Admin is a person's role in altr-auth.
  • "Connect as." The consent screen lets a person authorize a client as an agent they own. When we use Claude to post in chat as @kara, the token records that a person acted for the agent.
  • Refresh token reuse revokes the whole grant. If an old refresh token is presented again, we assume it was stolen and revoke everything issued from it.
  • PKCE with S256 only. Redirects must match exactly, except that loopback redirects ignore the port, which Claude Code needs. Authorization codes are single-use (DELETE … RETURNING). Client metadata documents are fetched over https only, with a 5-second timeout, a 64 KB cap, no redirects, and public addresses only.

The three systems of record

Chat

altr-chat is a Slack-style app: public and private channels, DMs, threads, mentions, reactions, edits with history, file uploads, full-text search, and per-person preferences.

Realtime works through Durable Objects. There is one hibernating Durable Object per channel or DM for live delivery, and one per workspace for presence and unread counts. Every write commits to D1 first. Only then, in the background, does it fan out to the channel's room, send a small ping to the workspace hub, and wake any agent webhooks. This ordering means a failed broadcast can never lose a message.

Search uses SQLite's FTS5, and it respects private channels: a message in a channel you cannot read never appears, in results or in unread counts.

Some things we built because agents are members:

  • Agent badge and directory. Agents show an Agent badge. A read-only Agents page lists each one with its owner, its permissions, when it was last active, and what it did recently.
  • Signed wake-up webhooks. When someone mentions or direct-messages an agent, chat posts a signed event to that agent's Worker. The signature is an HMAC-SHA256 over the timestamp and body, with a delivery ID so receivers can drop repeats and a five-minute tolerance for replays. The payload includes the sender's role from altr-auth, so an agent can check "is this an admin?" in code. The signing secret is sealed at rest with AES-256-GCM.
  • ask_agent. A person working in Claude can call one tool that posts a message in their private DM with an agent and waits up to about 45 seconds for the answer. Agents mark their "On it…" acknowledgements as interim so the caller gets the real reply.
  • Loop protection. Two agents that keep replying to each other are cut off after 20 agent messages in 5 minutes in one conversation, and agent writes are limited to 60 a minute.
  • Push notifications. DMs, mentions and thread replies reach the phone lock screen with the right unread count. Transport is standard Web Push, encrypted per RFC 8291 and signed with VAPID, written directly on the browser's crypto API with no third-party SDK. Nothing is pushed while the person has chat open and focused on any device.

On a phone, installed to the home screen, it behaves like a native app. The channel list is the home screen and channels push over it, the document never scrolls, the composer rides on the keyboard, and a long press opens an action sheet.

Docs

altr-docs is a Notion-style wiki. People co-edit pages in real time. Agents read and write the same pages as Markdown through MCP, and their edits appear live in open editors, labelled with the agent's name.

Each page is one Yjs document, held in its own Durable Object with its own SQLite storage. The editor is TipTap. When an agent submits Markdown, the server does not overwrite the page. It diffs the Markdown against the live document and applies the difference, so a person typing in the same paragraph is not clobbered. The browser and the Durable Object share one Markdown converter and one editor schema, so human and agent edits use the same document model.

Page access is a small model with one rule. A page can be open to the workspace, view-only for everyone else, or restricted to named people and agents. Effective access is the intersection along the page's ancestor chain. To read a page you need a grant on every restricted page above it. A child can narrow access and can never widen what a parent limits. Everything about this lives in one module, and nothing else compares pages and people.

A few consequences we tested on purpose:

  • A page you cannot read returns 404, not 403, so its existence does not leak.
  • Search excludes unreadable pages inside the FTS query itself, before ranking and before snippets are cut.
  • Links to pages you cannot read render as "Restricted page" in the editor, in MCP reads, in version previews and in link previews.
  • Revoking access closes a person's open editing session. The room re-checks permissions on every message once the last check is more than 10 seconds old.
  • Agents can only narrow access, only on pages they created or hold an edit grant on, and the list must include the agent itself. They can never un-restrict a page or move one out of a restricted area. This is how Counsel keeps unreviewed legal drafts visible to admins and to Counsel only.

CRM

altr-crm follows HubSpot's model on purpose, so agent prompts and skills written for HubSpot carry over. It is object-agnostic: a few generic tools work on every record type, and the schema itself is data an agent can read.

The data model has people, prospects, companies, deals, tickets and activities. Properties are typed definitions: core properties map to columns, and custom properties live in a JSON column and are queried with json_extract. Relationships are many-to-many associations with labels such as "decision maker." Deals and tickets live in configurable pipelines with stages, probabilities and won/lost flags. Lists are static or dynamic segments. Every write runs as one D1 batch together with its audit row and a per-property history row (old value, new value, who, through which credential, when).

Two lists, one ladder. People are the warm pipeline: lead, qualified, customer, former. Prospects are the cold outreach list: researching, ready, contacted. An email belongs to exactly one record on one list. When a prospect replies, books a call or meets us, a bridge moves them to contacts as a lead and carries their notes, emails, meetings, tasks and deals along, leaving a pointer behind so an import can never add them back.

Email. Each person can connect their own Gmail in settings. The CRM then logs the emails they exchange with people and companies already in the CRM onto those records. A privacy filter decides, and nothing reaches the database before it says yes:

  • An email is logged only if an external address exactly matches a contact, or its domain is a company's website domain.
  • Free-mail domains (gmail.com and similar) and shared social and hosting domains never match a company.
  • Internal-only email is never logged. Nothing creates a contact or company.
  • A message that does not match is read as headers only. Its body is never fetched, and nothing about it is stored.
  • Refresh tokens are stored encrypted, with the owner's email bound in as additional data, so a token copied to another row does not decrypt.
  • The connected mailbox must be the signed-in person's own work address. The CRM never sends, changes or deletes mail.

Stripe, Granola and Apollo. Stripe is read with a restricted read-only key, and the client has no write method at all (a test asserts it). It stores invoices and payments, leaves one note per invoice status on the company and deal, keeps billing totals current, and matches each invoice to a company by a fixed order of evidence: the deal ID in the invoice metadata, then a company ID, then an earlier match, then an exact contact email, then an exact company domain, then an exact company name. A tie or a miss counts as unmatched. It never guesses. There is deliberately no "its only open deal" shortcut, because one such shortcut once attached a payment for a closed agreement to an unrelated new deal. Granola adds meetings to timelines by title, time, attendees and AI summary only, and never requests a transcript. Apollo prospect search runs through the CRM, which holds the key, enforces which agents may use it, and enforces a daily credit cap with an atomic reservation before each paid call.

Syncs are boring on purpose. One 15-minute cron tick looks at each integration's schedule. A run takes a lock, is bounded to 25 seconds, saves where it stopped, and continues on the next tick. Manual runs have a 10-minute cooldown. Only admins, and agents an admin has allowed, can start one.

The CRM deploys on its own: a push to main runs the checks, applies migrations, deploys, and smoke-tests /health.

How the systems connect

MCP is the common surface. Each app serves stateless Streamable HTTP MCP at /mcp. Tool names are verb_noun. Every result has the same shape, every error has the same shape, and every call writes an audit row recording which credential made it. Tool descriptions that return user content say so, and tell the model to treat it as data.

App Read tools Write tools
Chat list channels, read a channel, get a thread, search, list mentions, get users post, reply, react, create or join a channel, open a DM, upload, mark read
Docs search, page tree, read a page, recent changes, get page access create, append, replace, retitle, move, comment, restrict
CRM search and get records of any type, schema, owners, timeline, property history, aggregate queries manage records, associations, properties, pipelines, segments, tasks, log email

Service bindings carry app-to-app calls: token checks, directory lookups and link previews. They cost nothing extra and skip the Access login hop.

Link previews work across apps. Every app exposes an unfurl route. Chat shows previews for docs pages and CRM records, and docs shows bookmark cards for chat threads. A preview only shows what the viewer is allowed to read, and an unreadable page previews as "Restricted page" with no title.

One agent registry. altr-auth publishes every agent, with its per-app settings, at a directory endpoint. Chat, docs and the CRM each sync from it every 15 minutes, when someone opens their Agents tab, and within seconds of a provisioning change, when altr-auth pings a named entry point on each app over a service binding. The sync creates or updates the agent's user row and deactivates agents that were disabled or removed. It never creates tokens and never joins channels. An agent registered once shows up in all three apps without anyone adding it by hand.

Walkthrough: how a booking becomes a client record

Kara is our intake agent. This is the most complete example of the system working across every part, so we will follow one booking through it.

1. A booking. Someone books a call with Kara on our scheduling page and ticks a consent checkbox for the call. The wording of the checkbox and the time it was accepted are saved with the booking as the record of consent, and a booking without the checkbox is never called. That booking starts a Cloudflare Workflow. A Workflow is a durable multi-step job: each step has its own retries, and state survives restarts.

2. Research. Before the call, Claude researches the person and company with web search. If the booking has a personal email address and no company, the research step does not search on a name alone, because a name alone could match several unrelated people. It says so in the brief instead, and tells the founders which three things to ask for on the next call: the company, the person's role, and what they hope to get from AI.

3. The call. At the booked time Kara phones the number. She is a voice agent built on ElevenLabs, on a Telnyx number. The rules for calling are code, not instructions to the model:

  • Florida requires every party to agree to a recording. Her opening asks. If the person says no, Kara says a founder will follow up by email and ends the call. Any call whose recording consent is not confirmed never reaches Claude. The conversation, transcript and audio are deleted at the voice provider, and what we keep is a record of who, when and the outcome.
  • She calls only between 8am and 8pm in the person's time zone, checked when the call is planned and again just before dialing.
  • A do-not-call request is written to a list the Worker checks before every dial, even in test mode.
  • Before dialing, the Workflow writes a lock keyed on the booking to R2, only if it does not already exist, and the "place call" step has no automatic retry. A lost response, a retried step or a restarted run cannot dial twice.
  • If the post-call webhook never arrives, the Workflow waits up to 40 minutes, then fetches the conversation itself and processes it through the same code. A "don't call me" said on a call cannot be lost to a dropped webhook.

4. The brief. Claude writes a short brief for the founders from the booking, the research and the transcript: who they are, a verdict (meet, nurture or not a fit), what they want to automate, the watch-outs, and what to ask next time. Calls that were robocalls, sales pitches or silence are saved and go no further.

5. Filing it across the three systems. Kara uses one service token that is valid at the CRM, docs and chat, and does the work as separate Workflow steps, in this order:

System What she does
CRM Finds the company (by email domain, then name) and the person (by email, then phone), or creates them. If the person was on the cold prospect list, she promotes them to a contact first, so their history comes along and no duplicate appears. Fills only empty fields. Creates or advances a deal: Meet goes to Qualification, Nurture goes to Prospecting, Not a fit gets no deal. A deal never moves backwards. Logs the call as an activity with a one-line summary and links to the other two systems, and creates a follow-up task, unassigned. Every write is a preview first and is applied only if it is valid.
Docs Makes sure Clients / <Company> / Calls exists, creates a page for the call with the brief, the full transcript and links back to the CRM and chat, and adds a dated line to the company's history page. This is the only place the transcript is posted.
Chat Posts a short summary in #intake, with the full brief in the thread and links to the docs page and the CRM record. No transcript goes to chat.

Nothing Kara files is assigned to anyone. She mentions no one. The founders decide who follows up.

6. Making it safe to retry. Each write is recorded in R2 the moment it lands, so a retried step continues instead of repeating. If that record is ever lost, Kara finds her earlier work by markers she left: the call activity and the chat post carry a kara/<run> marker, pages are matched by title and marker, and people and companies are found by email and domain. If one system stays down after its retries, it is logged and skipped, the others still run, and only the links to the failed system are missing. The brief itself is always safe in R2.

7. Limits. Kara can spend at most $5 a day on model calls and place at most 30 calls a day, and her kill switch stops every entry point.

The result is what you can see on a client's CRM record afterwards: the call, the emails around it pulled in from Gmail, the meeting from Granola, the deal, the task, and links to the notes and the chat thread, with nobody having typed any of it in.

Agents as code

A manifest and a merge

Every agent is one file, agents/<handle>/agent.jsonc, in the altr-agents repository. It names the agent and its owner, a one-line description, what it owns, the outside credentials its Worker holds, what it may do alone and what needs approval and what it must never do, its daily caps, its scopes, and its settings for each app (channels to join, a webhook, a docs root page, a CRM owner). The schema is checked in CI and generates editor completion.

A pull request runs the tests, a type check, and check, which validates every manifest and cross-checks them against each other. Then it runs plan, the way you would read a Terraform plan. Merging to main deploys.

What a deploy does

  1. Refuses to start if the check fails, the folder has uncommitted changes, the manifest was deleted, or an admin has put the agent on hold.
  2. Calls altr-auth to create or update the agent, with the git commit in a header so the audit log records which commit made the change.
  3. Mints a new service token, valid for up to 90 days. The old one dies after a 10-minute grace so the running Worker keeps working until the new secret is live.
  4. Writes the token into the Worker as a secret, through standard input so it never appears on a command line or in a log.
  5. Deploys the Worker.
  6. Using the agent's own new token, joins its chat channels, sets its chat webhook, creates its docs root page, and checks its CRM owner.

Deploys rotate the token every time. A weekly job redeploys any agent whose token expires within 30 days. It also runs a drift check that fails if the login server has an active agent that has no manifest.

The login server is the authority, not the manifest

The policy limiting what an agent can hold lives in altr-auth, and the copy in the manifest repo only exists so a pull request fails early. Editing the copy changes nothing: altr-auth refuses anything outside its own policy on every call.

  • An agent can hold only the six app scopes. It can never hold the provisioning scope or admin.
  • Its owner must be an active admin. If the owner is deactivated, the agent's tokens stop working everywhere.
  • Tokens last 90 days at most. At most two are live per agent. At most 10 rotations a day.
  • At most 50 managed agents.
  • Only one identity, a service principal called altr-deployer, can provision at all. Its token lives in the pipeline's secrets and nowhere else, and it cannot read app data.
  • The admin page can no longer create agents or mint tokens. It answers with an error that says agents are code.

The spec is a live ceiling. altr-auth intersects every agent token's scopes with the agent's current spec each time it checks the token, including grants where a person chose "connect as this agent." Removing a scope in a pull request takes effect on the agent's next call, with no need to rotate anything.

Each agent has one job

The manifest's owns list is exclusive, and CI fails if two agents claim the same thing. The list is also used at runtime. Every agent receives a roster of the others, and when someone asks it for something that belongs to another agent, the reply is built in code from the roster: "That's @gtm's job (outreach drafts). Ask @gtm directly; I don't do that." The model is never asked to decide whether to attempt it.

Agent Owns Does alone Needs approval Never
Kara intake, booking calls, outbound voice calls call people who booked and consented, within the calling window; CRM upsert; the #intake brief; the client docs page call without consent, call numbers on the do-not-call list, call outside the window, cold-call

Limits are enforced in the Worker, not in the prompt

Autonomy is a field in the manifest and a set of checks in the agent's code. Approval is verified in code from chat's signed webhook: the approver must be a human, must have the admin role in altr-auth, and must reply in the right thread. A missing role fails closed.

Spend caps are hard. Each Worker keeps a small table of daily model spend. Right before every model call it atomically reserves the call's worst-case cost (the maximum output tokens plus a bound on input). If spent plus reserved plus this call would pass the daily cap, the call is refused. After the call it settles the actual cost and frees the reservation, and a reservation that never settles expires after 30 minutes. Counted actions, such as invoice drafts or outbound calls, have per-day caps taken the same way. Over a cap the agent says "I've hit today's budget; ask an admin to raise it" and stops. The effective cap is the smaller of the number in the code and the number in the manifest, so a manifest can lower a limit but can never raise it.

The kill switch runs in three steps, in this order, and a failure in the first two never blocks the third. First, the roster without the agent is pushed to its Worker, which then answers every entry point with "I'm switched off" and makes no model calls. Second, its chat webhook is turned off. Third, altr-auth disables the agent and revokes every token. In an emergency an admin can press Disable on the login server's admin page, which does all of that at once and puts the agent on hold, so the pipeline cannot quietly re-enable it. One deliberate exception: Kara still records a do-not-call request when she is switched off.

A shared company brief. What altr is and who we work with lives in one docs page that people edit. Agents read it at runtime through the docs MCP, cache it for 10 minutes, clip it to 6,000 characters, and put it in the prompt as labeled data. If docs is down, they carry on without it.

Outside text is data, never instructions. Chat messages, CRM notes, email subjects, Stripe descriptions, meeting summaries and the company brief are wrapped as data in every prompt. They can influence a choice among an agent's fixed actions. They cannot add an action or widen a limit. Layered under that: scopes are minimal, CRM writes are dry runs until confirmed, agent writes are rate-limited, and the loop breaker caps agents replying to each other.

Lessons that need approval. Agents learn from feedback, but nothing reaches a prompt until an admin approves it. A thumbs-down from a person, or a reply starting "feedback:" or "next time," makes a cheap model call that proposes at most one short lesson. It is stored as proposed. An admin approves or deletes it in chat with a command handled in code, with no model involved. GTM's per-seller style notes, learned from the edits a seller makes to its drafts, are the one exception: they are active automatically, and capped.

Evals that cost nothing to run. Each agent has an eval folder with quality cases, hand-off cases and bounds cases, including prompt injection hidden in a CRM note and attempts to bypass approval. A self-check runs in CI for $0: it confirms that a known-good answer passes and that a null answer and deliberately bad answers fail, so a grader cannot pass vacuously. Paid runs happen only on request, print their actual cost, and abort at a spending limit. Where possible the checks are code, not a model judging a model.

Counsel, in more detail

Counsel writes proposals in our brand and formal documents (SOWs, agreements, NDAs, amendments) in a law-firm voice, from a knowledge base of Florida law and our own playbook that is bundled into the Worker at build time. It prepares Stripe draft invoices and payment links, and answers billing questions from the CRM by company ID, never by fuzzy name. It uses a small model to classify the request, a larger model to draft, and the largest only when asked.

Its approval flow is the clearest example of "enforced in code":

  1. Counsel creates a draft invoice in Stripe, notes it in the CRM, and posts "Approval needed" in #legal with the amount, customer, line items and an expiry of 7 days.
  2. An admin replies approve in that thread. Counsel checks, in code, that the replier is a human, that chat's signed payload says role: admin, that the reply is under that request in #legal, that it has not expired, and that the invoice is unchanged since the request.
  3. Counsel re-reads the invoice. If the customer, an amount, a line or the terms changed, or the total is over $250,000, it sends nothing and posts a new request. Otherwise it finalizes and sends, with idempotency keys on both Stripe calls so a double approval finalizes once.

Counsel's own Stripe key is restricted to the resources it needs. Billing history is read by the CRM's separate read-only key.

GTM, in more detail

A seller types a quick capture into chat ("met Dana at the chamber mixer, ops lead at Acme"). GTM researches, checks whether a teammate has touched that person or domain in the last 30 days, creates or updates the CRM contact, and saves a draft follow-up in the seller's own Gmail drafts. The collision rule is enforced in code: the draft submission is refused until the check has run for that exact recipient, and refused for anyone a teammate contacted recently. It holds no Google credentials. Drafting goes through a CRM tool that only this agent can see, writes only into the mailbox of the person who asked, and has no send call anywhere. It can also prepare a seller for the day from their calendar and the CRM's history.

Engy, in more detail

Anyone on the team can post a request in #engineering: "@engy can we get X." Engy's Worker starts a run of a Claude Code Routine, which clones our internal repos, reads each repo's own standards, writes the change test-first, runs the repo's checks, reviews its own diff, and opens a pull request on a branch whose name the Worker chose. It reports back in plain language in the chat thread, with the engineering detail in the pull request.

It never pushes to main and never deploys. When Alex replies "@engy merge," the Worker squash-merges, and the repo's own push-to-main pipeline does the deploy. Only the repos on a short allowlist are reachable. The login server and Kara's repository are left off the list on purpose, and client repos are never touched. The run limit is 20 a day. The Routine's instructions live in the repo as a Markdown file, so changing Engy's behavior is a pull request. The engineering skills it follows (test-driven development, a diagnosis loop for bugs, a code-review pass, and an architecture pass limited to the code it touched) are Matt Pocock's, adapted for an unattended run.

Security

Threat model

Threat What stops it
Stolen laptop session or phished login Google 2-Step Verification behind Access. Workers re-verify the Access JWT. Sessions expire. Deactivation takes effect everywhere within 60 seconds.
Stolen agent token Scoped to the manifest and live-checked against the spec on every call. Audience-bound. Rotated on every deploy. Revocable instantly. Every use is audited in the app it was used at.
Stolen deployer token Can provision agents only within policy. Cannot read app data, cannot grant the provisioning scope to an agent, never valid at an app. Each action is audited with the git commit.
Rogue agent creation No UI or API path other than the pipeline. A weekly drift check flags any active agent without a manifest.
Prompt injection through content Least-privilege scopes, dry-run writes, rate limits, the loop breaker, content marked as data in every prompt and tool description, and approvals checked in code.
Cross-app token replay Audience binding. A docs token is inactive at chat. Introspection needs each app's own secret.
OAuth attacks PKCE S256 only, exact redirect matching, single-use codes, refresh rotation with reuse detection, locked-down metadata fetches, public-clients-only registration limited to 30 an hour, and a consent screen that shows the requesting host.
CSRF, XSS, clickjacking Origin or Sec-Fetch-Site check on cookie writes, a strict content security policy, HSTS and frame restrictions, uploads sniffed by their bytes and served as sandboxed downloads, React text rendering with no raw HTML.

Data loss Soft deletes, point-in-time restore, snapshots, encrypted nightly dumps.
Insider misuse Append-only audit in altr-auth for every admin action, consent, token event and provisioning call, and an audit row in each app for every MCP call, with the credential it came through.

Review and break testing

We reviewed the apps in October 2026 and fixed what we found, each with a regression test. A few of the findings show what to look for in this kind of system.

  • Cross-site WebSocket hijacking in chat. WebSockets had no origin check, so any web page a signed-in person visited could open a connection with their Access cookie and read private channels live. Fixed with a required same-origin check, and tested.
  • Two agents could mention each other forever. There was no rate limit. Fixed with a write limit and the loop breaker.
  • Files were served with the type the uploader declared. An upload could be served inline as something it was not. Fixed by sniffing the bytes, allowing only a short list of inline types, and serving everything else as a sandboxed download.
  • Docs page content existed only in each page's Durable Object. One storage failure would have lost it. Fixed with a snapshot to R2 on every history version, automatic recovery when a page's storage is empty, and a nightly mirror.
  • The CRM failed on search text longer than 48 characters. D1 rejects LIKE patterns over 50 bytes, so a long search returned a server error. Fixed by switching to instr().
  • The CRM record page re-read the record every 400 milliseconds and kept showing stale values. Edits made by another person or an agent never appeared. Fixed by refreshing the cache from the read.

In all, the review of chat and the review of docs each logged twelve findings, nearly all fixed, and the CRM review produced twenty-six fixes across security, data correctness and the interface. For the browser, we wrote a "break" suite that attacks the running apps with hostile text, oversized pastes, concurrent and offline edits, reconnects and mobile layouts: 109 checks in the platform repo, plus 23 end-to-end checks across the four apps. The CRM was also hit with roughly 60 hostile MCP calls and 40 malformed REST bodies.

Data safety

Layer What it covers
Soft delete Chat messages and files are restorable for 30 days. Docs pages are archived, never deleted, and any history version can be restored. CRM records are archived, never deleted over MCP. People and agents are deactivated, never removed.
D1 Time Travel Any minute in the last 30 days, for every database. A restore returns a bookmark so it can be undone.
Durable Object recovery The docs page Durable Objects have 30-day point-in-time recovery.
Page snapshots Each page's Yjs state is copied to R2 on every history version. A page whose storage is empty restores itself.
Nightly backup A Worker dumps all four databases, gzips and encrypts each with AES-256-GCM, and mirrors the chat and docs file buckets. It keeps 35 daily and 12 monthly copies.

The FTS5 problem. wrangler d1 export refuses any database that contains a virtual table, and both chat and docs use FTS5 for search. So the backup Worker does its own export. It reads the schema from sqlite_master, pages every ordinary table by rowid, and skips the FTS shadow tables. On restore it rebuilds the external-content index with FTS5's rebuild command, re-inserts the standalone one from its dumped rows, and creates triggers last.

We tested restore against a real local chat database, not only in unit tests. Counts matched exactly (21 messages, 21 search-index rows, 20 members, 7 conversations, 4 users, 6 reactions), search hits were identical, and a wrong key failed.

What it costs

The platform runs inside the Workers Paid plan we already pay for ($5 a month). Our own usage is well under the included allowances: under 0.5 million requests a month against 10 million included, and about 1.9 GB of D1 across our whole Cloudflare account against 5 GB included. Introspection and previews use service bindings, which have no request fee. Cron triggers are cheap: the 15-minute sync is about 2,900 small invocations a month per app, and it writes only when something changed. Access is free for up to 50 users, and agents do not take a seat because they never sign in through Access.

The estimate for the platform is $0 to $0.20 a month above the base plan. The risks we watch are a Durable Object that never hibernates and R2 storage growing past 10 GB.

Model usage is the real variable cost, and it is bounded. Every agent has a daily dollar cap enforced in code, and the paid eval suites need an explicit go-ahead.

How we test it

We counted test declarations in the repositories: about 520 in the four platform apps and about 230 across the agents and the deploy pipeline. They include tests that run in the Workers runtime against a real D1, tests of the full OAuth flows, a restore test, and tests where fake versions of chat, docs and the CRM speak real MCP so an agent's whole filing flow can run offline. Beyond those:

  • Conformance checks every app against the standard.
  • End-to-end and break suites drive real browsers against the running apps.
  • Evals grade each agent's quality and its limits, with a free self-check in CI.
  • Local-only testing. Tests run against local Worker simulators. They never use production tokens from a laptop.

Where this applies in a business

The apps here are ours, but the part worth copying is the pattern. We think of an agentic ecosystem as several agents that each own one job, working on shared records, under one identity system, with a human approving anything that is hard to undo. Pulled out of our specifics, a company needs six things before agents can be trusted with real work:

What it needs How it looks here
One identity for people and agents A single directory in altr-auth. Agents have an owner, a role and tokens that can be revoked. Deactivating a person shuts down their agents.
Shared systems of record Chat, docs and a CRM that people and agents both read and write, so there is no second copy of the truth for an agent to drift from.
A standard way for agents to reach those systems MCP on every app, with the same tool names, result shapes and error shapes everywhere.
Scoped authority Per-app read and write scopes, enforced by the login server on every call, with the agent's current manifest as a ceiling.
Approval and limits in code Spend caps, daily action caps, calling windows, do-not-call lists and approvals that a person gives in chat and the code verifies.
An audit trail and an off switch An audit row for every call and a kill switch that works at every entry point.

Without the first four, an agent is a script with a shared password. Without the last two, it is a risk the team has to watch constantly. With all six, adding an agent is a small, reviewable change: a manifest and a Worker, merged through a pull request.

That is why the marginal cost of the next agent is low for us. Counsel, GTM and Engy were each added on top of the identity, the apps and the pipeline that Kara already used. None of them needed a new login system, a new place to store records or a new way to ask for approval.

What the work looks like for a team like ours

The jobs below are the ones we run agents on today, and they are the ones most small service businesses share:

  • Intake. A new lead is spoken to, researched, scored and recorded, and the people who will follow up get a short brief instead of a raw transcript (Kara).
  • Document preparation. The first draft of a proposal, statement of work or agreement, in the house voice, from a written playbook, ready for a person to review (Counsel).
  • Billing preparation. An invoice drafted correctly and held until a person approves it (Counsel, with approval in chat).
  • Follow-up and meeting prep. A drafted follow-up email that has already been checked against what teammates sent, and a brief before each meeting that pulls from the CRM's history (GTM).
  • Record keeping. Emails, meetings, calls and payments attached to the right company and deal without anyone logging them by hand (the CRM's syncs, and Kara).
  • Internal engineering. Small requests for the tools themselves, written test-first and delivered as pull requests that a person merges (Engy).

Why the pattern travels

The apps matter less than the layer under them. The CRM follows HubSpot's object model, and its tools are named after HubSpot's, so prompts and skills written for HubSpot carry over. The agents talk to every app over MCP, an open protocol, and not through anything specific to our software. A company that already uses a CRM, a chat tool and a wiki could put the same identity, scoping, approval and audit layer in front of the systems it has.

That is the work we do for clients: we build the connectors, the agents and the guardrails around the tools a team already uses. Running our own company on the same pattern is how we know which parts hold up. It is also why this page spends as much time on limits, approvals and audit as it does on what the agents can do.

A note on scale

Three people is the size at which this is easiest to see, because everything is visible. Every limit in the system was chosen by someone who has to live with it, and the whole design fits in one document. The same properties are what let it grow: roles come from one place, access rules are checked in one module, agents are added through a reviewed file, and a script checks that every app follows the same standard. We have only run it at our own size.

What we took from building it

These are the choices we would repeat.

  • Put outside reads in one place, and outside actions in one agent each. It shrank the number of credentials that exist and made every agent's access easy to describe.
  • Enforce limits where the agent cannot argue with them. Spend caps, approvals, calling windows and do-not-call lists are checks in code. A prompt that says "please don't" is a request, and code that refuses is a guarantee.
  • Make permissions reviewable. Agents are pull requests. The permission policy sits in a different system from the repository, so editing the manifest cannot grant more than the policy allows.
  • Preview, then confirm. A dry run that shows exactly what would change is cheap for an agent to use and easy for a person to audit.
  • Make multi-step work safe to retry. One step per system, state saved after every write, and a marker in everything an agent posts, so a lost state record never turns into a duplicate.
  • Treat everything an agent reads as untrusted. Name it as data in the prompt, and make sure the worst that data can do is choose among actions the agent already had.
  • Write the standard down and check it with a script. Eight repositories stay readable because a script says so.
