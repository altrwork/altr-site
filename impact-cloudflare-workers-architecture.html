We build AI connectors for clients. Cloudflare is why it takes days.

Most of what we build for clients is a connector. It is the least glamorous and most useful thing in applied AI: the piece that lets an assistant actually reach a company’s own records. You can ask Claude who owns a building, what a customer ordered last spring, or what is sitting in the contract folder, and it can only answer if something has handed it that data. That something is an MCP server, and we build ours on Cloudflare Workers.

That choice matters more for a company our size than it would for a large one. A connector used to be a project: a server to run it on, a deploy pipeline, monitoring, and somebody whose job is to notice when it stops. On Workers it is a file you publish. There is no machine to patch, no capacity to plan for, and no region to choose, and it is running in a few hundred cities the moment it goes live. For a two-person agency that is the difference between quoting a connector as a month of work and handing one over inside a week.

The thing that actually changed our pace, though, is that the platform is programmable the same way the product is. Everything Cloudflare offers sits behind an API, so creating a worker, provisioning a database, pointing a domain at it, adding a nightly schedule, or simply reading back what is currently deployed are all things we describe in a sentence and then watch happen. The infrastructure gets edited in the same conversation as the code. There is no context switch between writing a tool and giving it somewhere to live, which sounds like a small thing and is most of the reason a build stays in one afternoon instead of spilling across three.

It is also all in one account. Compute, the databases, DNS, the domains themselves and outbound email are native to the same platform, so there is nothing to stitch together and no afternoon lost to making four vendors’ credentials agree. When a connector we were building needed sign-in links, we did not go shopping for a mail provider. We added an email binding. Multiply that by every decision a new build has to make and it is most of a month nobody had to spend.

What a client ends up with is one connector that behaves differently depending on who is using it. Our servers hold nothing between requests, which means the same deployment can offer a different set of tools on each route: the valuation team gets valuation tools, capital markets gets recorded debt, property management gets its own. Opening a route for a new team is one line in a table and a redeploy, not a second deployment to maintain. It also means there is no long-lived session to leak, wedge, or migrate — every request starts from the same known state.

Their people install it themselves and sign in through a browser, so there is no token to paste into a config file and nothing sensitive sitting in a text file on somebody’s laptop. Because the connection knows who signed in, the assistant can write as well as read: create the contact, log the deal, generate the document, all as that person rather than as an anonymous service.

The part that makes this work as a business is that none of it becomes a permanent operations job. We are not running servers for the clients we build for, the cost scales with what actually gets used, and a connector that sits quiet for a week costs close to nothing. That is what lets a very small team say yes to building one, deliver it quickly, hand it over, and put the rest of the week into the next client instead of into keeping the last one online.
