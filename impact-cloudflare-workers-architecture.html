A commercial real estate chatbot, built by describing it.

We are building a chat assistant for commercial real estate. You ask it who owns a building, what debt is recorded against it, what it is probably worth, and it answers from county records rather than from memory. The whole thing runs on Cloudflare Workers, and the reason we chose to build there has less to do with performance than with how few afternoons it costs us.

The pitch for Workers is usually that your code runs in a few hundred cities and there is no server to patch. Both true, and both slightly beside the point for a team our size. The thing that actually changed how fast we move is that the platform is programmable the same way the product is. Cloudflare exposes everything through an API, so creating a worker, provisioning a database, pointing a domain at it, adding a nightly schedule, or reading back what is currently deployed are all things we describe in a sentence and then watch happen. The infrastructure gets edited in the same conversation as the code, which means there is no context switch between writing a feature and giving it somewhere to live.

It is also all in one account. Compute, the databases, DNS, the domains themselves and outbound email are native to the same platform, so there is no stitching four vendors together and no afternoon lost to making their credentials agree. When we needed sign-in links, we did not go shopping for a mail provider — we added an email binding. That sounds like a small thing. Multiply it by every decision a young product has to make and it is most of a month.

The shape it settled into is two Workers. One serves the product and its screens on its own domain. The other is the records connector that AI clients speak to, and it is the piece a broker actually installs. They reach each other over a service binding rather than a public HTTP call, so an internal request never leaves Cloudflare’s network, never crosses the public internet, and costs essentially nothing in latency. Underneath sit two databases: one holding accounts, billing and documents, the other holding the Florida corporate registry the ownership lookups run against.

Two scheduled jobs run on the same Workers. Florida publishes one corporate-filing file per day, so a Sunday run walks the previous eight days in a single pass, with enough margin that a late publish gets caught rather than missed — what it is watching for is an LLC formed to buy a building, which takes weeks to close, so a weekly cadence is comfortably ahead of it. A second job reconciles our billing against Stripe every morning. Neither needed a queue, a scheduler, or a machine left running.

The one design decision worth spelling out is that the connector is stateless. There is a common assumption that an AI server needs to hold a session per user, and Cloudflare offers Durable Objects for exactly that kind of stateful coordination. We had one early on and took it out. The connector now builds a fresh server for every request, which sounds wasteful and is the opposite: because nothing is held between requests, the same Worker can expose a completely different set of tools on each route — valuation, investment sales, debt, property management, or all of them — without a class per variant. Opening a route for a new team is one line in a table and a redeploy.

It also removes a whole category of problem. There is no long-lived object to leak memory, wedge itself, or need migrating between versions, and every request starts from the same known state. Durable Objects are the right tool when clients genuinely need to coordinate with each other — a shared document, a live room, an exact counter. A broker asking what a building sold for is not that, and pretending otherwise costs you complexity you then have to maintain.

The honest summary is that two people are running a product with scheduled ingest from a state registry, its own auth, billing, document generation and an AI connector, and almost none of our week goes into keeping it up. That is the whole reason to build this way. The time it saves does not go into more infrastructure. It goes into the next conversation with the next client.

Most software does not need a server any more.

An API, a scheduled job, a database and some screens is a shape that costs less, breaks in fewer ways, and is fast everywhere. We build them and hand them over.
