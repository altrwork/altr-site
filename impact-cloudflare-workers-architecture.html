Engineering

A commercial real estate chatbot, built and deployed by describing it.

We are building a chat assistant for commercial real estate: ask it who owns a building, what the debt on it is, what it is worth, and get an answer drawn from county records rather than from memory. All of it runs on Cloudflare Workers.

The reason we build there is that the platform itself is programmable the same way the product is. Cloudflare exposes everything through an API, so creating a worker, adding a database, pointing a domain at it, setting a nightly schedule or reading back what is deployed are all things we describe in a sentence and watch happen. The infrastructure is edited in the same conversation as the code.

It is also all in one place. Compute, databases, DNS, the domains themselves and outbound email are native to one account, so there is no stitching four vendors together and no afternoon lost to making their credentials agree.

The shape of the thing.

Two Workers, two databases, and no server anywhere in the picture.

An app and a connector

One Worker serves the product and its screens on its own domain. The other is the records connector that AI clients speak to. They reach each other over a service binding, so an internal call never leaves Cloudflare’s network or crosses the public internet.

Two databases and a mailbox

One database holds accounts, billing and documents; the other holds the Florida corporate registry the ownership lookups run against. Sign-in links go out through the platform’s own email binding, so there is no mail vendor in the path.

Work that happens while nobody is awake.

The same Workers wake on a schedule and do the jobs a person would forget.

The registry refreshes itself

Florida publishes one corporate-filing file a day. A Sunday run walks the previous eight days in a single pass, with enough margin that a late publish is caught rather than missed.

Billing reconciles itself

A second schedule checks the platform’s billing against Stripe every morning and repairs anything that drifted overnight.

Stateless on purpose.

The connector builds a fresh server for every request instead of keeping one alive per user.

One Worker, five tool sets

Because nothing is held between requests, the same Worker offers a different set of tools on each route — valuation, sales, debt, property management, or everything at once. Opening a route for a new team is one line in a table and a redeploy.

Less to go wrong

There is no long-lived object to leak, wedge or migrate between versions. Every request starts from the same known state, which is the cheapest correctness guarantee there is.

Built on

  • Cloudflare Workers, D1, DNS and Email

Most software does not need a server any more.

An API, a scheduled job, a database and some screens is a shape that costs less, fails in fewer ways, and is fast everywhere. We build them and hand them over.
