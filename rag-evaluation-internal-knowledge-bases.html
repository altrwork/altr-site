RAG evaluation for internal knowledge bases: test retrieval and answers separately.

A knowledge assistant that looks good in a demo can still be wrong on a third of the questions staff actually ask. Evaluation is how you find out before they do, and how you know whether this week's change made it better or worse.

Short answer

To evaluate RAG on an internal knowledge base, collect real questions with the source that answers each one, then score two things separately. Did retrieval find the right passage, and did the answer stay faithful to it? Include questions the system should decline. Rerun the same set after every change to prompts, models, chunking or permissions, and treat a drop as a failed release.

What should a RAG evaluation measure?

Two stages, scored apart, because they fail for different reasons and are fixed by different people. If the right passage never reached the model, no prompt change will help.

MetricQuestion it answersHow to score it
Recall at kWas the right source in the top k results?Automatic, against the expected source IDs
Context precisionHow much of what was retrieved was relevant?Model grader or labels
FaithfulnessIs every claim in the answer supported by the retrieved text?Model grader, checked against people
CompletenessDid the answer include the facts it had to?Checklist of required facts per question
Citation accuracyDo the citations point at the passage that supports the claim?Automatic where citations carry IDs
Correct refusalDid it decline when the sources do not answer, or the asker may not see them?Automatic, on the unanswerable items

Open-source libraries such as Ragas implement several of these under the names context precision, context recall, faithfulness and response relevancy. The names differ between tools, so define each metric in your own report.

How do you build a golden set?

From real questions, not invented ones. Pull them from the help desk, the team chat channel where people ask "does anyone know", and the assistant's own logs.

  • Start with about 50 questions and grow toward a few hundred as failures teach you what to add.
  • Cover the hard cases on purpose: exact identifiers, questions whose answer changed recently, ambiguous wording, answers spread across two documents, and questions with no answer in the sources.
  • Add permission cases: a question only managers may have answered, asked as someone who is not a manager.
  • Give every item an owner who can say what the right answer is, and a review date so the set does not go stale with the documents.
id: pto-carryover-2026
question: How many unused PTO days can I carry into next year?
expected_sources: [handbook-2026#time-off]
must_include: ["5 days", "must be used by March 31"]
must_not_include: ["10 days"]        # the 2025 policy
asked_as: employee
owner: people-ops
review_by: 2027-01-15

Can a language model grade the answers?

Yes, for faithfulness and relevance, if you check it. A model grader reads the question, the retrieved passages and the answer, and scores against a written rubric. It is fast and cheap enough to run on every change.

  • Calibrate it. Have a person score a sample of 30 to 50 items and compare. Where the grader and the person disagree, fix the rubric.
  • Make it show its work. Ask for the unsupported sentence and the passage it checked, not just a score.
  • Prefer exact checks where they exist. Whether a source ID is in the top five does not need a model to judge.
  • Keep the grader fixed between runs you compare. A new grader model changes the scores by itself.

How do you turn evaluation into a release check?

Run the set before any change to the prompt, the model, chunking, the index, the retriever or source permissions. Compare against the last accepted run.

  1. Block the release if any critical item regresses, such as a permission case or a safety answer.
  2. Block it if a headline metric drops past a threshold you set in advance.
  3. Report what changed, the metric deltas, the items that newly pass and newly fail, and who owns each failure.

How retrieval works, and why keyword search and reranking move these numbers, is in how RAG works.

Working rule

Score retrieval and answers separately, keep the question set fixed between runs, and make every failure someone's to fix.

Common questions

How many questions do you need to evaluate a RAG system?

Start with about 50 real questions that cover common requests, exact identifiers, recent changes and questions with no answer in the sources. That is enough to catch large regressions. Grow the set toward a few hundred as production failures show you what it is missing.

What is faithfulness in RAG evaluation?

Faithfulness measures whether every claim in an answer is supported by the passages the system retrieved. An answer can be correct in general and still unfaithful, if it adds facts the sources do not contain. It is the main measure of whether the system is grounded.

Can an LLM judge RAG answers reliably?

Reliably enough to run on every change, once calibrated. Have people score a sample, compare with the model's scores, and fix the rubric where they disagree. Ask the grader to cite the unsupported sentence, and keep the grader model fixed between runs you compare.

How often should you run a RAG evaluation?

Before every change to the prompt, the model, chunking, the index, the retriever or source permissions, and on a schedule even when nothing changed, because the documents themselves change. Treat a drop on critical questions as a failed release.

What is the difference between retrieval metrics and answer metrics?

Retrieval metrics, such as recall at k and context precision, measure whether the right passages reached the model. Answer metrics, such as faithfulness and completeness, measure what the model did with them. Scoring them separately tells you which part of the system to fix.
