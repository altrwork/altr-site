How to design an MCP server for internal AI tools.

A production MCP server should expose narrow tools with typed schemas, least-privilege access, predictable errors, approval gates for sensitive writes, and complete audit records. Treat the server as a security boundary around internal systems—not as a thin wrapper around every available API endpoint.

By altr · Updated August 9, 2026 · 5 min read

Design principle

We design MCP servers like internal APIs with stronger operating rules. Each tool needs a clear boundary, typed inputs, predictable outputs, audit records, and an owner who accepts the risk of read or write access.

What should an MCP server expose?

A good MCP server design begins with a list of jobs the agent is allowed to perform. Examples include searching CRM notes, reading support tickets, drafting a refund request, or opening a deployment report.

The owner should define the input, the data touched, the expected output, and the failure mode for each tool. Broad tools create ambiguous behavior. Small tools make permissions, testing, and review easier.

The official MCP architecture guide separates tools, resources, and prompts into discoverable server capabilities. That separation is useful when deciding whether the model should take an action, read context, or start from a reusable interaction template.

How should MCP permissions work?

Read tools should return only the data needed for the task. Write tools should require stronger auth, narrower scopes, idempotency keys, and human approval for material changes.

This split gives technical leaders a clean control point. A support agent can search order history without permission to issue refunds. A deployment assistant can inspect logs without permission to change production settings.

Why do MCP tool schemas matter?

Model Context Protocol tools should expose strict schemas for inputs and outputs. Required fields, enums, limits, and validation errors tell the agent what it can ask for and tell engineers what they need to test.

Good schemas also protect downstream systems. They prevent free-form database filters, oversized payloads, hidden writes, and vague success messages. The output should include enough source detail for a person to verify the result.

How do you test and audit an MCP server?

Internal AI tools need logs that record the caller, tool name, input summary, source system, result status, approval state, and correlation ID. These records should be searchable by engineering and operations owners.

Local testing should cover success paths, permission failures, malformed inputs, empty results, rate limits, and approval gates. The handoff point is explicit: the agent proposes, the server records, and the human approves high-impact writes.

For remote servers, use the protocol's current Streamable HTTP transport and test the full authorization flow. Cloudflare's remote MCP server guide documents authenticated and unauthenticated deployments and recommends the MCP Inspector for local verification.

Working rule

Give every MCP tool one job, one owner, one auth path, and one auditable result.

MCP server design checklist

  1. Give each tool one clear business job and a named owner.
  2. Separate read operations from writes and grant the minimum required scope.
  3. Define strict input schemas, bounded outputs, and actionable error responses.
  4. Require confirmation or human approval for irreversible and high-impact actions.
  5. Log the caller, tool, input summary, approval state, result, and correlation ID.
  6. Test normal, malformed, unauthorized, empty, rate-limited, and replayed requests.

Frequently asked questions

Should one MCP tool wrap an entire API?

Usually not. A narrow task-oriented tool is easier for a model to select, easier for engineers to test, and easier for security owners to authorize. Keep low-level flexibility behind the server unless the client genuinely needs it.

When should an MCP write require human approval?

Require approval when a write is difficult to reverse or could affect money, customer communication, production systems, access rights, legal obligations, or employee records. Lower-risk idempotent changes may use policy-based automation with logging and bounded permissions.
